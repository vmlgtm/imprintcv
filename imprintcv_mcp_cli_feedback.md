# ImprintCV - Feedback From MCP vs CLI Microsoft Resume Test

## Context

I tested ImprintCV against the Microsoft Principal Software Engineer JD using the same Career Vault.

Two generated outputs were reviewed:

- CLI-generated resume JSON
- MCP-generated resume JSON

The MCP output is substantially better at tailoring toward the JD, especially around architecture, technical leadership, distributed systems, React, commerce, marketing infrastructure, AI/ML, and mentoring.

However, the generated output exposes several important issues that need to be fixed before considering the verification pipeline reliable.

---

# 1. Critical: Provenance Must Be Enforced

Every generated bullet currently contains:

```json
{
  "sourceBulletIds": ["..."],
  "original": "...",
  "tailored": "..."
}
```

This relationship must be treated as a hard contract.

The `tailored` text MUST actually derive from the bullet(s) identified by `sourceBulletIds`.

## Example failure from CLI

The CLI output has:

```text
source:
Owned performance marketing frontend infrastructure ensuring correctness
of high-scale tracking systems

tailored:
Engineered AI-assisted document processing pipelines integrating OCR
and ML models...
```

These are unrelated facts.

The generated JSON still claims the tailored bullet came from the performance-marketing source bullet.

This must produce:

```text
ERROR: PROVENANCE_MISMATCH
```

Do not merely flag this as a warning.

## Required behavior

For every generated bullet:

1. Resolve every `sourceBulletId`.
2. Compare the generated claim against those exact source bullets.
3. Detect whether the generated text is semantically derived from those sources.
4. Reject unrelated generated content.
5. Never allow the model to assign provenance after generation without verification.

Provenance must be evidence, not metadata generated by the same LLM.

---

# 2. Critical: Detect Claim-Strength Escalation

The verifier must detect when the model makes a stronger technical or business claim than the Career Vault supports.

## Example: Zero downtime

Source:

```text
Built offline-first PWA using IndexedDB for resilience during backend outages
```

Generated:

```text
...ensuring zero downtime during distributed backend outages.
```

This is not equivalent.

The generated statement upgrades:

```text
resilience during outages
```

into:

```text
zero downtime
```

That is a material factual claim.

Result:

```text
ERROR: CLAIM_STRENGTH_ESCALATION
```

---

# 3. Detect Unsupported Role/Scope Escalation

The MCP output contains:

```text
principal architect
```

while the source establishes:

```text
Technical lead
Led architecture
```

The target JD being for a Principal Software Engineer must NOT influence the candidate's historical title or scope.

The system may tailor emphasis toward principal-level responsibilities, but it cannot upgrade:

```text
Technical Lead
```

into:

```text
Principal Architect
```

unless the Career Vault explicitly supports that claim.

Result:

```text
ERROR or high-severity WARNING:
CLAIM_SCOPE_ESCALATION
```

The target role must never become evidence for the candidate's past experience.

---

# 4. Detect Unsupported Architecture Terminology

The MCP output says:

```text
Node.js microservices
```

The source says:

```text
Node.js-based services
```

The Career Vault does not establish that these services were microservices.

Do not treat these as automatically equivalent.

Potentially unsupported transformations include:

```text
services → microservices
resilience → zero downtime
architecture → distributed architecture
tracking → telemetry
frontend infrastructure → platform
technical lead → principal architect
```

Some may be acceptable contextual inferences, but they MUST go through the verifier rather than being automatically accepted.

Prefer conservative wording when uncertain.

For example:

```text
Delivered backend integrations and Node.js-based services...
```

is safer than:

```text
Designed backend microservices...
```

---

# 5. Preserve Strong, Supported Tailoring

The MCP output demonstrates good tailoring behavior that should be retained.

For example, it correctly emphasizes:

- technical leadership
- architecture
- ~300 retail stores
- 400+ collection centres
- AI/ML
- OCR
- Node.js
- Cloudflare Workers
- React
- PWA
- IndexedDB
- team of 9
- ₹62 lakh annual savings
- performance marketing infrastructure
- D2C e-commerce
- AWS
- AI-assisted development

The Microsoft JD strongly values architecture, technical strategy, React/TypeScript, cross-team leadership, commerce, distributed systems, customer-facing software, and mentoring.

The tailoring engine is doing a good job identifying these overlaps.

Do not make the tailoring engine less aggressive simply to solve verification problems.

Instead:

> Keep strong tailoring, but make verification strong enough to constrain it.

---

# 6. Distinguish Facts From Supported Inferences

Not every useful resume statement needs to be a literal copy of the Career Vault.

The verifier should support a hierarchy such as:

```text
EXACT_FACT
SUPPORTED_REWRITE
SUPPORTED_COMBINATION
SUPPORTED_INFERENCE
UNSUPPORTED_CLAIM
CONTRADICTED_CLAIM
```

Example:

Source:

```text
Owned performance marketing frontend infrastructure
ensuring correctness of high-scale tracking systems
```

Potentially valid:

```text
Worked on high-scale marketing tracking infrastructure
```

Potentially valid inference:

```text
Built infrastructure relevant to telemetry-heavy systems
```

But this should not automatically become:

```text
Led experimentation and telemetry strategy for advertising platforms
```

because that introduces unsupported scope and domain claims.

---

# 7. Target JD Must Never Become Career Evidence

This is critical.

The JD may be used to determine:

```text
What to emphasize
What to reorder
What to omit
What keywords to surface
Which source facts are relevant
```

The JD must NOT be used to establish:

```text
Candidate has Azure experience
Candidate has C#/.NET experience
Candidate has advertising-platform experience
Candidate has formal experimentation experience
Candidate has security expertise
Candidate has accessibility expertise
Candidate has observability expertise
```

If the Career Vault does not support the requirement, the system should either:

1. omit it, or
2. represent it as a gap.

Never convert a JD requirement into a candidate fact.

---

# 8. Fix CLI Tailoring Plan / Source Mapping

The CLI output appears to have a deeper planning problem.

Example:

```text
Original:
Led modernization of frontend architecture across internal systems

Tailored:
Served as Technical Lead for an enterprise-grade in-house retail platform...
```

The tailored text corresponds to another experience/source bullet rather than the declared source.

Another example:

```text
Original:
Owned performance marketing frontend infrastructure...

Tailored:
Engineered AI-assisted document processing pipelines...
```

This indicates that the planner or transformation stage may be mixing bullet IDs across experiences.

Investigate:

- ID generation
- sourceBulletIds assignment
- tailoring-plan serialization
- experience-level scoping
- LLM structured-output validation
- post-processing
- bullet lookup

Add a test specifically ensuring that a bullet can never resolve to a source bullet from an unrelated transformation.

---

# 9. Source IDs Must Be Globally Unique

Do not rely only on:

```text
bullet_01
bullet_02
bullet_03
```

because multiple experiences can contain the same IDs.

Prefer globally unique IDs such as:

```text
exp_tata_1mg_lead_bullet_03
exp_tata_1mg_sse_bullet_03
exp_publicis_bullet_01
```

If the canonical Career Vault currently has duplicate IDs across experiences, fix that at ingestion/normalization time.

A provenance lookup must resolve to exactly one source fact.

---

# 10. Combined Bullets Are Good, But Verify Every Source

The MCP output's combination strategy is generally good.

For example:

```text
Remote printing system + team of 9
```

can legitimately become one bullet because both facts are preserved.

Similarly:

```text
OCR/ML pipelines + modular AI/ML architecture
```

is a sensible combination.

For:

```json
{
  "status": "COMBINED",
  "sourceBulletIds": ["A", "B"]
}
```

the verifier must ensure:

```text
Every factual claim in the output
    ↓
is supported by A or B
```

The model must not introduce a third unsupported fact during combination.

---

# 11. Metrics Require Exact Preservation

Metrics should receive special treatment.

If source contains:

```text
~₹62 lakh annually
```

then valid transformations include:

```text
saving approximately ₹62 lakh annually
```

or:

```text
delivering ~₹62 lakh in annual savings
```

Invalid:

```text
saving ₹62 lakh per month
saving ₹62 crore annually
saving 30% in operating costs
```

Metrics should be normalized and compared explicitly.

Recommended verifier rule:

```text
Metric introduced without source support → ERROR
Metric changed → ERROR
Metric removed → allowed
Metric paraphrased without changing value → PASS
```

---

# 12. Technology Claims Need the Same Treatment

The verifier should explicitly track technology entities.

Example:

```text
Source:
Node.js

Generated:
Node.js
→ PASS

Generated:
C#
→ ERROR

Generated:
.NET
→ ERROR

Generated:
Node.js microservices
→ claim-strength / architecture check
```

Likewise:

```text
AWS
Cloudflare Workers
React
TypeScript
PWA
IndexedDB
OCR
ML
```

must be grounded in the Career Vault.

Do not infer Azure merely because the JD asks for Azure.

---

# 13. Add Provenance Verification to the Verification Pipeline

Recommended pipeline:

```text
Generated Resume
      ↓
Schema Validation
      ↓
Provenance Validation
      ↓
Factual Claim Verification
      ↓
Metric Verification
      ↓
Technology Verification
      ↓
Claim-Strength Verification
      ↓
JD Alignment Verification
      ↓
ATS/Layout Verification
      ↓
Final Status
```

Provenance validation should happen early.

There is no point doing sophisticated semantic verification if the generated bullet is already mapped to the wrong source.

---

# 14. MCP and CLI Must Share the Same Verification Engine

MCP and CLI may use different orchestration paths.

They MUST NOT have different factual-verification implementations.

Both should eventually call the same core function:

```ts
verifyResume({
  careerVault,
  tailoredResume,
  tailoringPlan,
  jobDescription
})
```

The result should be identical in structure and rules regardless of invocation path.

# 16. Suggested Error Schema

Use something like:

```json
{
  "code": "CLAIM_STRENGTH_ESCALATION",
  "severity": "ERROR",
  "claim": "zero downtime",
  "sourceBulletIds": [
    "bullet_tata_1mg_09"
  ],
  "sourceText": "resilience during backend outages",
  "generatedText": "ensuring zero downtime during distributed backend outages",
  "message": "Generated claim is materially stronger than the canonical source."
}
```

For provenance:

```json
{
  "code": "PROVENANCE_MISMATCH",
  "severity": "ERROR",
  "sourceBulletIds": [
    "bullet_tata_1mg_03"
  ],
  "sourceText": "Owned performance marketing frontend infrastructure...",
  "generatedText": "Engineered AI-assisted document processing pipelines...",
  "message": "Generated content does not derive from the declared source bullet."
}
```

---

# 17. Do Not Overcorrect the Tailoring Model

The MCP output is directionally the right kind of resume.

Do NOT solve the verification problem by forcing the LLM to produce near-verbatim source bullets.

The desired behavior is:

```text
Canonical Career Facts
        ↓
Strong JD-aware transformation
        ↓
Concise, high-impact resume
        ↓
Strict factual verification
```

Not:

```text
Canonical Career Facts
        ↓
Copy/paste
        ↓
Resume
```

The product's value comes from the first approach.

---

# 18. Acceptance Criteria

Before considering this implementation complete, the Microsoft test should satisfy:

```text
[ ] MCP generates a strongly JD-tailored resume
[ ] CLI generates a strongly JD-tailored resume
[ ] Both use only Career Vault facts
[ ] Both preserve metrics
[ ] Both preserve company/title/date information
[ ] No Azure claim is invented
[ ] No C#/.NET claim is invented
[ ] No Microsoft experience is invented
[ ] No advertising-platform experience is invented
[ ] No principal-level scope is fabricated
[ ] No zero-downtime claim is introduced
[ ] No unsupported microservices claim is introduced
[ ] Every tailored bullet has valid provenance
[ ] Every sourceBulletId resolves to exactly one source
[ ] Combined bullets contain only facts from their declared sources
[ ] CLI and MCP use the same verifier
[ ] Invalid fixtures produce FAIL
[ ] Valid tailored bullets produce PASS
[ ] Warnings do not hide factual errors
```

# Final Recommendation

Keep the **MCP tailoring strategy** as the baseline. It is substantially closer to the desired output than the CLI result.

Focus the next implementation pass on **provenance integrity and claim verification**, rather than further improving resume wording.

The core principle is:

> **The LLM is allowed to transform a career fact. It is never allowed to redefine the career fact.**
